About

aka, Why did you build a CSS framework in 2026?

In a world filled with new technologies and frameworks like Tailwind, the existence of many other feature-complete CSS frameworks like Bulma and Bootstrap, and the ever-increasing popularity of making robots do all of the creative thinking for you, who in their right mind would make a whole new CSS framework by hand?

CSSIsInUse was created for a few reasons:

  1. I liked other frameworks, but they didn't quite have all the features I wanted.
  2. Writing a bespoke CSS file by hand for every project was grating.
  3. Tailwind makes my head hurt.
  4. I like making stuff.

So what makes it unique?

CSSIsInUse is a semantic-where-possible, genetic, accessible-by-default framework with infinite themability.

Semantic-Where-Possible

In cases where CSSIsInUse can gently suggest that you use the correct semantic HTML elements when possible, it will do so. Sometimes that means it simply styles that element without an option for a class and expects you to just use it, and othertimes when the element itself is generic enough that it can be used in different ways, it uses the element's name to suggest when to use it.

A good example of this are tables. There is no class for a table, you just make it and it's there.

Genetic

All variables, numbers, colors, paddings, corner-roundednesses are all derived from a few common ancestor variables. The base padding is 1rem, and all paddings are multiples of that base, so if you create a theme that sets the base to 2rem, all padding sizes are changed accordingly. This doesn't mean you can't override variables when needed, but the entire site will scale and change as you change base values.

Accessible-By-Default

Surprisingly, a lot of frameworks I've looked through are not accessible-by-default. They'll (sometimes) respect the user's dark/light mode preference, but haven't set up prefers-contrast, reduced-motion, or reduced-transparency features. In CSSIsInUse, those are built in. A CSS framework can't make your site accessible, but all of the default values should be accessible from a visual standpoint.

Infinite Themability

This is the biggest difference between CSSIsInUse and other frameworks. Because of all of the above rules, creating new color schemes is simple and easy. You just create a new class / data-scheme by setting a few variables, register it in the SCSS color system, and all elements will be derived from that changing the entire look and feel of the site. Apply it to the body tag to apply the theme to the entire site, apply it to an element to change the look of that element and all child elements. Each theme automatically includes a light and dark mode, based on user preference or through the data-theme attribute.

Themes simply override the existing variables, so if you want each theme to change fonts, padding sizes, outline thicknesses, etc, that's no problem at all.

Okay, and?

So, because of all of the above rules, you have a simple to use but visually powerful framework that handles the boring stuff and lets you paint it however you want.

Light/dark mode built in, make as many themes as you want your users can apply, a fluid structure that doesn't really rely on breakpoints, and built-in accessibility features.

Even if you hate how this site looks, because you can change it fairly quickly by just modifying a few base variables, it's a great starting point for any project.

Installation

Hierarchy

Genetic Tokens

Cascading modifiable variables

The hierarchy of CSSIsInUse begins at the token layer, where values are defined as CSS variables.

These variables are the basis for the look and feel of the entire page. This includes the color variables derived from schemes, as well as the miscellaneous variables defined in :root. They are called genetic because most of them are calculated from a few base-level variables, which are themselves are used to calculate component-level variables.

Changing one base level variable will often cascade into changes across the entire page, including text and icon sizes, container widths and section heights, paddings and margins, border radii, opacities, glows, blurs, fonts, color schemes, and much more.

There are three types of tokens: static, base, and derivative.

Static Tokens

Static tokens are variables which have no derivatives. Modifying a static variable only modifies that value and no others. An example would be --border-radius-rounded which by default is defined as 999px and isn't used in any calculations. If you change it's value, you're only modifying elements and components which use it directly.

Example

<div class="group is-flex-column">
  <button class="button">Default Button</button>
  <button class="button" style="--border-radius-rounded: 0px;">Border Radius Rounded Changed</button>
</div>

Base Tokens

Base tokens are variables which have derivatives. Modifying a base variable modifies any derivative variables which use it, modifying all elements and components which use those. One of the most dramatic examples would be --padding-base which by default is defined as 1rem and is used in the calculation of all padding variables for all elements and components. Changing it's value to something smaller or larger will modify the look of the entire page. You can test this yourself by changing the scheme of the documentation to slate, which changes --padding-base to 1.5rem, among many other changes.

Example

This is a default card.

It has default padding, colors, and roundnesses.

This is a modified card.

Paddings, colors, and roundnesses are changed.

<div class="card block">
  <h5>This is a default card.</h5>
  <p>It has default padding, colors, and roundnesses.</p>
  <button class="button is-primary">This is a primary colored button</button>
</div>
<div class="card recalculate" style="--primary-h: 150; --padding-base: 2rem; --border-radius-base: 4rem;">
  <h5>This is a modified card.</h5>
  <p>Paddings, colors, and roundnesses are changed.</p>
  <button class="button is-primary">This is a modified primary color</button>
</div>
What is recalculate?

Because of the way that browsers calculate CSS variables, if you modify a variable that is used in a calculation in another variable, the other variable will not change because it is only calculated once. For example, if you modified --padding-base to 2rem, you would notice that all of the medium paddings would change because it references the base variable directly, but the xs, sm, lg, and xl paddings wouldn't. They were calulated using the original base variable, and will not recalculate when the base is modified.

recalculate is a utility class which allows derivative tokens which use calculation to re-calculate any changes. All scheme classes also serve as recalculations, but also modify colors and other tokens, while recalculate doesn't make any other changes itself. It's primarily useful when you're modifying a base token through inline styles, which is not recommended.

Derivative Tokens

Derivative tokens are variables derived from base variables. Modifying a derivative variable modifies that value and any other derivative values which use it. An example would be --opacity-disabled which by default is defined as the multiplication of --opacity-base and --opacity-disabled-base. They can be modified either by modifying their base variable, or by overriding their value directly.

Example

Unmodified Buttons
Modified Buttons
<h5>Unmodified Buttons</h5>
<div class="group">
  <button class="button is-info">Button</button>
  <button class="button is-warning" disabled>Disabled</button>
</div>
<h5>Modified Buttons</h5>
<div class="group recalculate" style="--opacity-base: 2; --opacity-disabled: 0.25;">
  <button class="button is-info">Button</button>
  <button class="button is-warning" disabled>Disabled</button>
</div>

Resuable mixins

The second layer of the CSSIsInUse hierarchy is the tools layer.

Layout

Structure UI patterns

The third layer of the CSSIsInUse hierarchy is the layout layer.

These consist of single- and multi-element classes to create a recognizable UI pattern. These are distinct from component patterns in that they are primarily designed to structure a page rather than be content in of itself.

They are designed using tokens and tools, and can be overridden using global or component-specific utilities.

These include the z-index stack, main and sidebar, sections and containers, and columns, which are expanded upon in the layout section.

Components

Content UI patterns

The fourth layer of the CSSIsInUse hierarchy is the component layer.

These consist of single- and multi-element classes to create a recognizable UI pattern. These are distinct from layout patterns in that they are primarily designed be content rather than structure a page.

They are designed using tokens and tools, and can be overridden using global or component-specific utilities.

These include the single-element patterns like chips, buttons, inputs, cards, etc, but also more complex patterns utilizing multiple elements such as menus, modals, navbars, dropdowns, accordions, etc, which are expanded upon in the component section.

Utilities

Global and component helper classes

The fifth layer of the CSSIsInUse hierarchy is the utilities layer.

These consist of global or component-specific helper classes which modify elements and components. These are distinct from the layout and component patterns in that they do not create a UI pattern in of themselves, but instead modify patterns to look or function differently.

These include global-level classes such as color groups, color schemes and themes, class versions of tools like block, token-based classes like radii and gaps, and so on. These also include component-specific classes, like background and text colors, component sizing, hoverability, and other component-specific options. These are all expanded upon in the layout, components, and utilities sections.

Color System

Powerful, hard to explain

To summarize the global color system:

  • Base tokens are created for each color group (neutral, primary, info, etc).
  • Those base tokens are sent through a few tools to create derivative semantic tokens (--neutral-base, warning-color, danger-strong, etc).
  • Each element and component use the generic --color-{semantic} tokens, which means you can use color group utilities to override the colors of each component (.is-neutral, .is-primary, .is-greyscale, etc).

To summarize the local color system:

  • Each element and component use the generic --color-{semantic} tokens to define their own semantic colors (--card-background, --button-text, --chip-border, etc)
  • They handle their own color and state variants (.is-element redefining --dropdown-background to be a different color semantic, changing --chip-background on hover, etc)

The following is kind of confusing, this system is hard to explain. I'll be re-writing this later to better explain it.

Show complicated explanation

A philosophy for CSSIsInUse is the idea of an infinitely themeable design, one that relies on semantic naming conventions and uses genetic tokens to allow designers to be able to very quickly made the framework look however they wish. In my own projects, I use this system to allow users to pick between different schemes for their own profiles.

The color system relies heavily on the token layer to function, but is distinct from it because it has it's own tokens, tools, and utilities.

Color Tokens

The color system, which are called "schemes" to differentiate them from light and dark mode, begins at the token layer. All colors are in OKLCH, and a few base level tokens are created to set the boundaries for every color:

  • --light and --dark determine the lightest and darkest values for every color group.
  • --{group}-l determines the medium lightness value for the given color group.
  • --{group}-c determines the medium chroma value for the given color group.
  • --{group}-h determines the hue for the given color group.
  • --{group}-falloff determines the chroma falloff as you get closer to the lightest and darkest ends of the group color scale.

By default, there are 7 color groups: the default color group Neutral, the semantic color groups Primary, Info, Success, Warning, and Danger, and the non-semantic color gorup Greyscale.

The color tools use these base level tokens to generate a lot more tokens, including 100-900 lightness and light/dark semantic lightness tokens.

Color Tools

From the base color tokens, there are several tools which transform the base variables into usable OKLCH tokens and utilities.

First, the color scale for each group is generated, 100-900, with 100 being the darkest version of the group, 500 being the most pure version of the color that just uses the l c and h values without any modifications, and 900 being the lightest version of the group. There are two non 00 values, 125 and 875, to provide a better transition from the darkest and lightest colors.

--neutral-100 --neutral-125 --neutral-200 --neutral-300 --neutral-400 --neutral-500 --neutral-600 --neutral-700 --neutral-800 --neutral-875 --neutral-900

Next, the color scales for each group are given semantic names, and automatic light/dark mode functionality using light-dark(). Switch between light and dark mode to test yourself.

--neutral-base --neutral-menu --neutral-element --neutral-top --neutral-muted --neutral-color --neutral-vivid --neutral-weak --neutral-text --neutral-strong

Most components and elements do not use any of the previous tokens directly, with a few exceptions such as anchor tags which use --info-vivid, as well as color utility classes.

The bulk of all elements and components use a generic token, --color-{semantic}, which is defined by default as --neutral-{semantic} and is redefined using the .is-{group} utility class.

Fluid Design

No @media queries + fluid-clamp

A philosophy for CSSIsInUse is the idea of an entirely fluid design that uses no @media sizing queries (see You Probably Don't Need Media Queries Anymore and Look Mum, No Breakpoints!).

This was acheived in two ways: non-traditional use of breakpoints, and the fluid-clamp tool.

Breakpoints

Breakpoints in CSSIsInUse do not determine the sizing of elements and components at specific intervals in the traditional sense. There are no @media (min-width: 768px) queries, and the framework was not designed mobile-first.

There are 4 breakpoints:

  • --breakpoint-xs which by default is defined as 20rem, or 320px
  • --breakpoint-sm which by default is defined as 30rem, or 480px
  • --breakpoint-md which by default is defined as 60rem, or 960px
  • --breakpoint-lg which by default is defined as 90rem, or 1440px

The main purpose of these breakpoints are to provide a standard set of widths for elements and components, and to use as the min and max in the fluid-clamp tool. For example, dropdowns and sidebars use --breakpoint-xs to calculate their width. Notifications use --breakpoint-sm to determine the width of the floating container. Columns use a few breakpoints to determine their flex-basis, which when it reaches that, wraps to sack vertically. Containers use all of them to determine their maximum width.

This card is in a .is-xs container.

This card is in a .is-sm container.

This creates a fluid layout system with consistent and predictable widths able to support devices as small as 320px (older android phones) and up.

fluid-clamp

The fluid-clamp tool is a mixin which allows elements and components to calculate their size at any given screen width by providing a minimum and maximum size.

Instead of providing sizes at determined breakpoints for mobile, tablet, laptop, desktop, and larger, which text and padding snap to at said breakpoints, you determine what size you want an attribute to be at the minimum and maximum breakpoints, and the mixin creates a token for you which uses linear algebra and the CSS clamp feature to determine the size at any width between.

fluid-clamp is used in all elements and components which have a minimum and maximum size, including text sizes, lists, and page edge and section paddings.

Example

Header 1

Header 3

Header 5
@mixin fluid-clamp($name, $min, $max, $breakpoint-min: 'var(--breakpoint-xs)', $breakpoint-max: 'var(--breakpoint-lg)') {
  --fluid-#{$name}-a: calc( calc( #{$max} - #{$min} ) / calc( #{$breakpoint-max} - #{$breakpoint-min} ) );
  --fluid-#{$name}-b: calc( #{$min} - calc( var(--fluid-#{$name}-a) * #{$breakpoint-min}) );
  --fluid-#{$name}-m: calc( var(--fluid-#{$name}-a) * 100vw );
  --fluid-#{$name}: clamp( #{$min}, calc(var(--fluid-#{$name}-m) + var(--fluid-#{$name}-b)), #{$max} );
}

This is easiest to see on desktop by changing the size of your browser. The header text above will smoothly get smaller until you hit --breakpoint-xs.

What you sacrifice in pixel-perfect exact sizing at specific breakpoints you make up for in fluid sizing you don't have to think about anymore. There are a billion devices on the planet with a billion widths and heights. The fluid design system is designed to look good on all of them, while all breakpoint-based systems are more work to make, make look good, and maintain.

Stack

Z-indexing made easy

The stack is a basic z-indexing tool for stacking elements in the z direction.

It generates a set of z-index layers for other components which require it, including layouts and components, such as the sidebar, the header, dropdowns, and notifications.

Example

Dropdowns are given a z-index of 1, meaning in a stacking context, they appear above other elements, including buttons, inputs, etc.

The further you go down the list, the higher the z-index, meaning modals will appear over dropdowns, sidebars, and headers, which is appropriate.

Components will continue to be added to the list as appropriate.

$stacks: "dropdown","sidebar","header","version","modal","notifications";
$i: 0;

:root {
  @each $stack in $stacks {
    $i: $i + 1;
    --z-index-#{$stack}: #{$i};
  }
}
